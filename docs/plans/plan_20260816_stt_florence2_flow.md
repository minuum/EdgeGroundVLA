8개 점질량을 학습한다.** → soda 재수집이 선행조건이며, 우리가 대신할 수 없다.

## 3. 교수님 의도 해석 (추정 — 확인 필요)

~~Florence-2를 OWL-v2 대체 검출기로 보면 성립하지 않는다~~ →
**2026-08-17 실측 결과 검출기로도 가능성이 열렸다**(§2-B). 다만 재현율이 남은 과제다.
그리고 **π0와 묶어 보면** 백본 통합 쪽이 더 큰 그림이 된다 — π0 = `PaliGemma(VLM) + flow-matching action expert`.
그 자리에 Florence-2를 넣으면:

1. **백본 2개 → 1개**: 현재 OWL-v2 0.155B + Kosmos-2 vision 0.303B = 0.458B.
   Florence-2-base는 0.23B 하나로 grounding·caption·detection을 태스크 프롬프트로 처리
   → **경량화 논문 방향과 정확히 일치**
2. **언어 경로 복원**: 우리는 text attention 0%라 엄밀히 VLA가 아니다. Florence-2는 실제
   텍스트 인터페이스를 가져 CH68(언어조건화)로 연결된다
3. **flow matching = cadence 문제의 구조적 해결**: 현재 1.9초 그라운딩 때문에 1.3Hz로 판단하고
   zero-order hold로 버틴다. cadence-aligned 학습은 브리핑 자체가 *"근본 해결책이 아니라
   저비용 완화책"*이라 적고 있다. **action chunking은 한 번 추론으로 H스텝을 뱉어 지연을
   분산시키는, 병목 자체를 겨냥한 해법이다.**

즉 의도는 "검출기 교체"가 아니라 **"검출+분류기 파이프라인에서 벗어나 진짜 VLA가 되자"**로 읽힌다.

## 4. STT 설계 — 두 축 모두 옵션으로 유지

사용자 결정: **범위·발화방식 둘 다 옵션으로 두고 수집 단계에서 양쪽 다 확보**한다.

### 4-1. 축 ① — 언어가 무엇을 바꾸는가

| 옵션 | 내용 | 난이도 | VLA인가 |
|---|---|---|---|
| **T1. 타겟 선택** | "바구니로 가" / "의자로 가" → 그라운더 쿼리 교체 | 낮음 (배선 완료) | ❌ 언어가 정책에 닿지 않음 |
| **T2. 주행 방식 지시** | "왼쪽으로 돌아서 가" / "천천히" → 정책 자체가 변함 | 높음 | ✅ 사다리 ② |

T1은 부품이 다 있어 즉시 데모 가능하지만, **그것만으로는 "음성으로 검출 대상을 고르는 리모컨"**이다.
T2가 되어야 사다리 ②의 permutation/counterfactual 검정을 통과할 수 있다.

### 4-2. 축 ② — 언제 말하는가

| 옵션 | 내용 | 데이터 구조 영향 |
|---|---|---|
| **U1. 에피소드 시작 전 1회** | 지시 → 주행 → 종료 | instruction이 에피소드 속성 (1:1) |
| **U2. 주행 중 수시 발화** | 주행 도중 목표/방식 변경 | instruction이 **시계열** (t별 유효 지시) |

**U2를 나중에 추가하려면 U1 데이터로는 불가능하다** — 에피소드당 1개 문자열만 있으면
"언제부터 이 지시가 유효한가"를 복원할 수 없다. 그래서 **수집 시점에 U2 구조로 저장**하고,
U1은 그 특수 케이스(발화 1건)로 다룬다. 이것이 이번 수집 스펙의 핵심이다.

### 4-3. 수집 스펙 (soda 요청안) — 한 번에 다 받는다

```
에피소드당 저장 항목
  기존: images, actions(8-class LUT)
  추가 A: actions_raw   — 조이스틱 아날로그 원값 (lx, ly, az), 이산화 이전
  추가 B: utterances    — 발화 시계열, 항목당 {t_start, t_end, text, audio_path?}
  추가 C: instruction_timeline — 프레임별 "그 시점 유효 지시" 인덱스 (U2 복원용)
```

- **A**는 flow matching의 전제 (블로커 A 해소)
- **B·C**는 언어 조건화의 전제
- **셋을 같은 세션에서 동시에 받는다** — 따로 받으면 두 번 수집해야 하고,
  더 나쁘게는 두 배치가 서로 다른 조건이 되어 apples-to-apples가 깨진다

## 5. 주행 중 지시 변경 (U2) — 필요한 구성

현재 서버는 `predict(image, instruction)`으로 매 호출 phrase를 받으므로 **문자열 교체 자체는
이미 가능하다.** 문제는 교체 순간 **서버 내부 상태가 옛 타겟 기준으로 남는다**는 것이다.

### 5-1. 타겟 전환 시 오염되는 상태 (코드 실측)

| 상태 | 위치 | 전환 시 문제 | 조치 |
|---|---|---|---|
| `_grounding_cache` | `:769` | 옛 타겟 bbox를 최대 2프레임 재사용(`skip_n=3`) | **즉시 무효화 필수** |
| `history` (6프레임 윈도우) | `:859` | bbox 4채널이 옛 타겟을 가리킴. vis 256d는 타겟 무관이라 오염 아님 | flush(콜드스타트) vs 6프레임 자연 감쇠 — **택1 필요** |
| `stop_latched` | `:862` | 옛 타겟에 이미 STOP 래치면 **새 지시를 영원히 무시** | **해제 필수** |
| `inference_count` | `:767` | 콜드스타트 가드·skip_n 모듈로 기준. 유지 시 새 타겟에 가드 미적용 | 정책 결정 필요 |
| `get_goal_area(phrase)` | `:267` | phrase별 정지 area 임계값 | 매 호출 조회라 **자동 반영, 조치 불요** |
| ground filter map | `:276` | phrase별 min_cy/min_area | 동일 — 조치 불요 |

현재 `reset()`(`:882`)은 전부 초기화하는 all-or-nothing이라 **타겟 전환용으로는 과하다**
(에피소드 자체가 새로 시작되어 버림). → **`switch_target()` 소프트 리셋을 신설해야 한다.**

### 5-2. 신설이 필요한 구성요소

1. **`switch_target(new_phrase)` API** — 캐시 무효화 + STOP 래치 해제 + (선택)윈도우 flush를
   원자적으로 수행. 프레임 경계에서만 적용되도록 pending 큐 경유.
2. **비동기 STT 수신 경로** — Whisper 추론은 수백 ms~수 초. 제어 루프(~1.3Hz)를 막으면 안 되므로
   `/audio/transcript` 구독 → pending 명령 슬롯에 적재 → 다음 `predict()` 직전에 소비.
3. **발성 트리거(웨이크워드 또는 push-to-talk)** — 없으면 주변 대화가 목표를 바꾼다.
   **안전상 필수**이며, 수집 때도 발화 구간(t_start/t_end) 확정에 필요하다.
4. **전환 안전 규칙** — 회전 중 타겟이 바뀌면 과회전 위험. 전환 시 **1스텝 STOP 후 재획득**을
   기본값으로 둔다(§7.2 회전 안전 규칙과 동일 계열).
5. **명령 조정(arbitration)** — 인식 실패/저신뢰도 발화 처리. Whisper confidence 임계값 미달이면
   무시하고 직전 지시 유지 + 사용자에게 피드백(대시보드/음성).

### 5-3. 미해결 설계 질문 (승인 전 결정 필요)

- **윈도우 flush 여부**: flush하면 새 타겟에 깨끗하지만 6프레임 동안 시간 맥락이 없다
  (콜드스타트 재발). flush 안 하면 혼합 윈도우로 몇 프레임 부정확. **실측으로 정할 문제.**
- **U2 라벨 정의**: 발화 t_start부터 유효인가, 발화 종료(t_end)부터인가? 사람은 말하면서
  이미 조작을 시작하므로 **t_start 기준이 실제 인과에 가깝다**고 보나 검증 필요.

  **permutation 하락 ≥5%p 또는 counterfactual flip 방향 일치**.
- **5단계**: 이산 헤드(실기 95/100) 대비 실기 성공률 **비열등**. 연속 헤드가 실기에서
  더 나쁘면 채택하지 않는다(val 지표로 판정하지 않음 — 핵심 발견 6번).
