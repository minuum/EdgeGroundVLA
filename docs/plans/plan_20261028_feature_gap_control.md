# 계획: A(고정 융합 특징) 대 B(DaViT 풀링) 격차의 원인 분리 + 실기 시험 후보 (구현 승인 전)

> 작성일: 2026-10-28 | 상태: **계획(사용자 검토용, 구현 금지)** | 근거: `e2e_general.json`, `e2e_fullstage.json`, `gap_wm.json`, `precompute_v6_florence2_fused.py`, Florence-2 `modeling_florence2.py::_encode_image`
> 용어: "비교 조건" = 같은 데이터·분할·지표에서 한 가지만 바꾼 실험 한 줄.

## 0. 이전 해석의 정정 (중요)
10/28에 "A는 프롬프트와 이미지가 섞인 다중모달 인코더 출력이고, B는 텍스트와 무관한 평균 풀링이라 공간 정보를 잃어서 격차가 난다"고 설명했다. **코드를 확인한 결과 둘 다 틀린 부분이 있다.**
- A의 특징(`feat`)은 `_encode_image` 출력의 **577토큰 평균**이다(`precompute_v6_florence2_fused.py:50,57`). 프롬프트(텍스트)는 들어가지 않는다. "fused"는 같은 인코딩 한 번으로 bbox 생성과 특징 추출을 함께 한다는 뜻이다. → **언어 융합 가설은 폐기.**
- A도 평균 풀링을 쓴다. → **"B는 평균 풀링이라 공간 정보를 잃는다"만으로는 A와 B의 격차를 설명할 수 없다.**
- 두 경로의 실제 차이(`_encode_image`, `modeling_florence2.py:2598~2642`): DaViT 출력에 ① 학습된 2D 위치 임베딩을 더하고 ② 전역 평균 토큰 1개를 덧붙인 뒤 ③ `image_projection`(1024→768)과 `image_proj_norm`(LayerNorm)을 **토큰마다** 적용하고 ④ 그 후 평균한다. B0는 DaViT 토큰을 곧바로 평균(1024)하고 투영(`Proj`: LayerNorm→Linear→GELU)을 **평균 뒤에** 적용한다.
- 지금 가능한 정직한 서술: "같은 DaViT를 쓰지만 평균을 내는 위치와 Florence의 투영 경로가 달라 A와 B가 다른 특징을 갖고, 성능 차이가 났다. 원인은 미확인." 그리고 **전처리 불일치(입력 픽셀 경로 차이) 가능성도 아직 배제하지 못했다.**

## 1. 목표
A와 B의 방향 오차 격차(19.6° 대 29.6°)가 (a) 구현·전처리 차이인지, (b) 평균을 내는 순서(토큰별 투영·정규화 후 평균)인지, (c) 위치 정보 보존 여부인지를 가른다. 가설을 확정하는 것이 아니라 원인 후보를 하나씩 제거하는 실험이다.

## 2. 비교 조건 (모두 같은 3분할, 같은 FM-π0 헤드·bbox 창·라벨·120 epoch)
입력은 기존 캐시 `runs/e2e_cache/stage2.npy`(DaViT 단계2 출력, 4,984×2304×512 fp16)에서 단계3(conv3+block3)을 거친 토큰을 사용한다. 이 토큰에 Florence의 `image_pos_embed`·`image_projection`·`image_proj_norm`을 그대로 적용할 수 있다.

| 이름 | 특징 만드는 법 | 알려주는 것 |
|---|---|---|
| A | 기존 고정 융합 특징(캐시) | 기준 |
| B0 | 단계3 토큰 평균 → Proj (기존, 768 입력) | 기준 |
| **R0 (복원 대조)** | 단계3 토큰 → Florence 투영 경로(위치 임베딩·전역 토큰·투영·LN) → 평균 = A 재현 | **먼저 A의 캐시와 코사인 유사도 확인.** ≈1이면 파이프라인 동일, 벗어나면 전처리 차이가 격차의 원인 후보 |
| R1 | R0 경로로 만든 특징으로 헤드 학습 | R0이 A를 재현하면 R1≈A여야 함(구현 오류 점검) |
| P1 | 투영된 토큰을 3×3 격자로 평균(9토큰 × 128로 채널 축소 후 결합) | 위치 정보 보존 효과 |
| P2 | 투영된 토큰을 가로 방향 8구간(높이 평균)으로 평균 | 방향은 cx(가로)가 결정하므로 가로 위치만 보존 |
| P3 | 학습형 어텐션 풀링(질의 1개 + 위치 임베딩) | 평균 대체 |

추가(비용 큼, 필요할 때만): A의 입력 픽셀 경로(JPEG 압축 여부 등)와 B 입력 캐시 `px768.npy`의 경로가 같은지 비교 — 비용이 낮아 R0 단계에서 함께 점검한다.

## 3. 단계와 기준
1. **R0 복원 점검**(학습 없음, 몇 분): 같은 프레임에서 R0 특징과 캐시 A의 코사인 유사도·노름을 측정. **0.99 이상이면** 파이프라인 일치로 보고 2단계로. 그 미만이면 불일치 원인(전처리·dtype·해상도)부터 찾고 이후 비교를 중단.
2. **R1, P1, P2, P3 학습**(3분할 × 4조건 = 12회, 학습 1회 약 5분, 약 1시간): 
   - R1이 A와 ±1° 안이면 구현 일치.
   - P1·P2·P3 중 **R1 대비 방향 오차가 3° 이상 낮아지면** 위치 정보 보존이 효과가 있는 것. 낮아지지 않으면 평균 풀링은 원인이 아니다(그 결과도 기록).
   - S(반사실 민감도)도 함께 본다. 위치 정보를 보존해도 S가 오르지 않으면 "입력에 정보가 없어서"가 아니라 "학습 신호·라벨 문제"라는 증거가 된다(서보 라벨 계열과 연결).
3. 결과가 모호하면 seed 3개로 확장(조건당 9회).

## 4. 변경 파일 (승인 후)
- **신규** `scripts/eval_feature_gap.py`: `eval_e2e_general.py`의 `pooled_all`·`Proj`·`head_loss`를 가져다 쓰고, Florence 투영 경로는 로드한 모델의 `image_pos_embed`·`image_projection`·`image_proj_norm`을 직접 호출. 기존 파일 수정 없음.
- 출력: `docs/v5/egvla2_fm/feature_gap.json`, 로그 `runs/e2e_cache/logs/feature_gap.log`.
- Florence-2는 `HF_HUB_OFFLINE=1`, `.venv`(peft·transformers 있음)에서 실행.

## 5. 위험
- R0가 A를 재현하지 못하면 이후 비교의 해석이 불가능하다(그 자체가 중요한 발견이므로 1단계에서 멈춘다).
- 단계2 캐시는 해상도 768 기준이다. 384 비교와는 섞지 않는다.
- P1~P3가 개선되어도 오프라인 방향 오차일 뿐 폐루프 효과는 별개다.

## 6. 일정
- R0 점검 10분 이내, 학습 12회 약 1시간. GPU가 현재 비어 있어 승인 즉시 시작 가능.

# 실기 시험 후보

## 현재 오프라인 결론이 실기 시험에 주는 의미
- **배포 후보가 아닌 것**: E2E 조건(B1·B2, 방향 오차 27~37° 대 A 19.6°), 월드 모델 보조 헤드(S 개선 없음). 실기에서 돌릴 이유가 없다.
- **실기에서 가릴 가치가 있는 것**: S를 올린 서보 라벨 계열(오프라인에서 S +3~20°, 사람 방향 오차 +9~22°)이 폐루프에서 이득인지 — 오프라인 지표로는 결론이 나지 않는다.
- 실기 폐루프 성공률(300회)은 아직 한 번도 측정하지 못했다.

## 단계별 제안 (모든 시험은 로봇 세션에 직접 전달하지 않고 핸드오프 문서와 커밋으로 전달, 사용자가 중계)
| 단계 | 시험 | 규모 | 목적 | 판정 |
|---|---|---|---|---|
| R1 | A0(기준 `C_pi0_adaln_drop30_e120.pt`) 대 A1(A0 + `SERVO_BLEND=0.5`) | 각 pos1×5 타깃 위치×4회 = 20회 | 서버 쪽 서보 혼합만으로 효과가 있는지(모델 교체 없이 가장 저렴) | 성공률·타깃 이탈·정지 위치 |
| R2 | A2(servolabel 0.5)·A3(servolabel 1.0)·A4(MLP 회귀)·A5(E1b_tuned) | 각 20회 | 오프라인 맞교환(S 대 방향 오차)이 폐루프에서 어느 쪽이 이득인지 | R1과 같은 지표, 같은 조건 |
| R3 | 시작 회전·속도 보정 실험(`HANDOFF_20261023_ROBOT_PHYSICAL_CALIBRATION.md`) | 소규모 | 모델 밖 요인(속도 0.7 대 1.0, 회전 정지 특성)이 격차의 몇 %인지 분리 | 영상 이동량 대 명령 |
| R4 | 최선 조건 확정 후 pos2·pos3 추가 + 반복(최종 300회 설계의 일부) | 규모 큼 | 일반화·재현성 | 성공률 신뢰구간 |

- 권장 순서: **R1 → (결과에 따라) R2 → R3 병행**. R1에서 A0와 A1 사이에 차이가 없고 둘 다 실패하면 서빙 보정보다 모델·데이터 문제로 좁혀진다.
- 이미 만들어 둔 문서: `HANDOFF_20261027_ROBOT_MODEL_ARMS.md`(체크포인트·sha256·환경변수). 로봇 쪽 회신(10/22~10/27 핸드오프 수신 여부)과 pos2/pos3 드라이런 10건은 **확인되지 않았다**. 사용자가 로봇 세션의 수신 상태를 확인해야 한다.
- 규모 중 가장 큰 결정: 20회 × 6조건 = 120회가 현실적인가(로봇 시간 기준). 사용자 판단이 필요하다.

## 승인 요청 사항
1. R0 복원 점검과 R1·P1·P2·P3 비교 조건, §3 기준 동의 여부
2. 실기 시험 R1부터 시작할지, R2까지 한 번에 요청할지(로봇 가용 시간)
