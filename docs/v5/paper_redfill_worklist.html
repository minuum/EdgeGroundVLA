본문 수정1.3절 — MLP 행동 헤드 서술

p5 · 1.3. Lightweight MLP Action Head
🔴 문제 상황 — 초안 본문(검은 글씨)
📄 초안 본문 인용
융합된 256차원 특징은 4개의 hidden layer로 구성된 MLP 행동 헤드에 입력되어, 3자유도(3-DoF)와 이산 행동 공간에 대한 8개 클래스 중 하나로 분류된다.

두 가지가 틀렸습니다 — 입력 차원과 layer 수. 요구 원문 06번이 "1560차원"을 명시하고 있어 같은 문서 안에서 값이 충돌합니다.

✅ 대응책 — 실제 구조
초안실제
입력256차원1560차원 (6프레임 × 260)
hidden layer4개2개 (512 → 128 → 8)

빠진 것: bbox 4채널이 서술에 없고, window=6이 반영되지 않았습니다. 시간 문맥을 쓴다는 점이 헤드 설명에서 사라진 셈입니다.

근거: MLPActionHead in scripts/train_exp73_trackA_heads.py

본문 수정1.2절 — Feature Fusion 서술

p5 · 1.2. Feature Fusion via Linear Projection
🔴 문제 상황 — 초안 본문(검은 글씨)
📄 초안 본문 인용
두 인코더에서 추출된 특징은 Linear projection(1024→256)을 통해 동일한 차원의 임베딩 공간으로 매핑된 후, L2 정규화를 적용하여 스케일을 통일한다. 이 융합 표현은 이후 행동 헤드의 입력으로 사용된다.

"두 인코더 특징을 같은 공간에 매핑해 융합"이 실제 구조와 다릅니다. OWL-v2 출력은 projection을 통과하지 않습니다.

✅ 대응책 — 실제 융합 방식

projection 출력 256차원은 비전 경로만입니다. OWL-v2 출력은 스칼라 4개(cx, cy, area, has_bbox)로 직접 concat됩니다.

bbox 4ch (projection 미통과)
  +  비전 256ch (1024 → image_proj → L2norm)
  =  260ch  →  × bbox_scale 3.0  →  window 6 flatten  →  1560
정확한 서술은 "이종(heterogeneous) 특징을 같은 공간으로 사상하는 것이 아니라, 저차원 기하 정보와 고차원 시각 문맥을 그대로 병치(concatenate)한다"입니다. → 이 편이 절 제목 Heterogeneous와도 맞습니다.

검증 상태 — 코드 기본값은 0.25이고 운영에서 0.20을 환경변수(VLA_OWLV2_THRESH)로 주입합니다. 7/23 세션 27건의 runtime_config에는 owlv2_thresh = 0.25로 기록돼 있습니다 (PG2-448 그라운더 시기). 0.20은 실기 담당자 보고와 CH64 64-17 기준이며, 100건 테스트 세션 원본 H5가 현재 로컬에 없어 직접 확인하지 못했습니다 → 논문 기재 전 재확인 필요.

10 p5 #64 skip_n=3 의미

파라미터 이름만 있고 무엇을 하는지, 왜 필요한지, 무엇을 잃는지가 없습니다. 이 값은 제어 주기를 결정하는 핵심 설정입니다.

✅ 대응책 — 무엇으로 채우는가

grounding_skip_n=3 — 매 프레임 그라운딩하지 않고 3프레임마다 한 번 수행하고, 사이 프레임은 마지막 bbox를 유지합니다(zero-order hold). 실효 그라운딩 주기 약 1.3Hz.

왜 필요한가 — OWL-v2 검출이 젯슨에서 1901.7ms, 전체 지연의 약 97%입니다. 매 프레임 호출하면 제어 주기가 성립하지 않습니다.

무엇을 잃는가 — bbox가 최대 2프레임 낡습니다. 회전 중에는 이 지연이 조향 오차로 직결되므로 원문 11의 재그라운딩 규칙이 함께 있어야 성립합니다. 두 항목을 따로 쓰면 안 되고 한 묶음으로 서술해야 합니다.

11 p5 #65 force_reground_on_miss - 회전 후 강제 재그라운딩

이름과 한 줄 설명만 있습니다. 실제로는 회전 관련 보호 규칙 3개가 함께 걸린 묶음이라, 하나만 쓰면 동작을 재현할 수 없습니다.

✅ 대응책 — 무엇으로 채우는가

미검출 시 skip 주기를 무시하고 즉시 재그라운딩합니다. 함께 걸린 규칙:

  • 회전 직후 강제 재그라운딩 (추론 서버, 상시) — just_rotated = self._last_pred_class in (6, 7) 이면 skip_n과 무관하게 재검출합니다
  • 회전 지속 0.4초 제한 — 과회전으로 타겟이 시야를 벗어나는 것을 막습니다
    ⚠️ 위치 주의: 이 규칙은 추론 서버가 아니라 제어 계층에 있습니다 — VLAControlManager(move_duration=0.4) (robovlm_nav/serve/vla_control_utils.py). 제어 루프는 행동을 COAST 4.0초 동안 10Hz로 반복 발행하는데 회전만 예외로 move_and_stop_ramped()로 약 0.4초 돌고 자동정지합니다(이동·횡이동은 반복 발행 유지).
    이유(2026-07-30 주석): 예외가 없으면 그라운딩 ~2초 동안 같은 회전이 10Hz로 계속 재발행되어 논스톱 회전이 되고, weak_left 세션들에서 타겟이 화면 밖으로 밀려나는 원인으로 확인됐습니다.
    ※ 추론 서버 안의 0.4는 무관하게 회전 방향을 정하는 cx 임계값(cx < 0.4 → ROT_L)입니다 — 같은 숫자가 두 곳에 있어 혼동하기 쉽습니다.
  • 연속 회전 차단 (추론 서버, 상시) — blocked_second_rotation = (pred in (6,7) and last_pred in (6,7)) 이면 회전을 실행하지 않고 정지 명령([0,0])으로 대체합니다. "차단"보다 정지로 치환이 정확합니다
force_reground_on_miss는 상시 규칙이 아닙니다 — VLA_FORCE_REGROUND_ON_MISS 기본값이 "0"(off)이고 코드 주석에 "A/B 테스트용, 기본 off"로 명시돼 있습니다. 7/23 세션 27건의 runtime_config에도 이 키가 없습니다 → "항상 적용된다"고 쓰면 안 됩니다.
이 절의 핵심 논지 — 이 규칙들이 존재하는 이유는 미검출을 학습으로 처리하지 못했기 때문입니다. 학습 데이터의 has_bbox=False가 0/16,599 = 0.00%라 모델은 "지금 못 보고 있다"에 대응하는 법을 배운 적이 없습니다(CH64 64-15).
→ "학습 공백을 서빙 로직으로 메웠다"가 이 절의 정직한 프레이밍이고, 원문 25의 서술과 정확히 이어집니다.

② 에피소드·프레임은 대칭인데 액션 클래스는 비대칭입니다 — 그리고 원인이 좁혀졌습니다
전체 격차는 좌계열 3,384 vs 우계열 4,122 = 21.8%인데, 두 트랙으로 분해하면:
묶음좌계열우계열격차
트랙 A (좌우 시작 180ep) 2,8203,551+25.9%
트랙 F (중앙 시작 45ep) 564571+1.2%
트랙 A에서만 발생하고 트랙 F에서는 사실상 없습니다.
게다가 정렬 회복에 쓰는 조향 자체는 좌우 대칭이었습니다 — 강좌 시작의 우계열 19.2% vs 강우 시작의 좌계열 19.9%(0.7%p 차), 약좌·약우 쌍도 1.6%p 차입니다.
실제로 다른 건 직진 비중입니다 — 좌측 시작 49~51% vs 우측 시작 40~41%(약 10%p 낮음)로, 우측 시작에서 조향을 더 많이 썼고 그 초과분이 우계열 총량을 키웠습니다.
→ 어느 한 방향의 조향을 회피한 게 아니라, 시작 위치에 따라 사용한 조향의 총량이 달랐던 것으로 해석됩니다 (관측에 대한 해석이며 조작 로그로 검증한 것은 아닙니다).
→ 대응 방법이 달라집니다: 에피소드·프레임이 이미 대칭이므로 좌측 데이터를 더 모아도 해결되지 않습니다. 실제 대응은 클래스 가중치 + 미러 증강(65-9)이었습니다. 이것이 CH66 사슬의 출발점입니다.

15 p8 #126 학습 파라미터 16 p8 #127 window = 6 프레임 bbox_scale = 3.0 17 p8 #128 num_classes = 8 optimizer = Adam, lr = 5e-4 18 p8 #129 epochs = 300 scheduler = CosineAnnealingLR 19 p8 #130 class weight = 1/빈도 정규화 ← FORWARD 71~74% 편중 보정 20 p8 #131 seeds = 0, 1, 2 (다중 시드로 분산 확인)

파라미터 값은 정확하지만 재현에 필요한 것이 빠져 있습니다 — 특히 분할 방식이 없습니다. 분할을 안 쓰면 정확도 수치의 의미가 확정되지 않습니다.

✅ 대응책 — 무엇으로 채우는가

추가해야 하는 3가지

  • 분할: 에피소드 단위 15% val, SPLIT_SEED=42. 프레임 단위가 아니라 에피소드 단위인 점이 핵심 — 같은 에피소드 프레임이 train/val에 섞이면 누출입니다
  • hold-aware 샘플링: stride=5로 결정 시점마다 1샘플, 라벨은 [t, t+5) GT의 다수결. 서빙의 zero-order hold(원문 10)와 학습을 일치시키는 설계입니다
  • 학습 대상: MLP 헤드 0.866M만, 나머지 전부 frozen — 체크포인트 실측 865,928 파라미터로 교차 확인
  • batch size 128, 모델 선택은 25 epoch 간격 검증 중 최고 시점 (300 epoch 중 13개 후보)
    • ⚠️ 요구 원문 17번 자체의 오류 — 원문은 optimizer = Adam이지만 코드는 AdamW(weight_decay=1e-4)입니다.
    요구 원문 04번(bbox_scale)에 이어 원문 자체가 틀린 두 번째 항목입니다.
우리가 실제로 데인 적이 있습니다 — 초기 DEPLOY 실험에서 train_one(Xtr, ytr, Xtr, ytr, …)로 학습 데이터를 val로 넣는 버그가 있어 94.5%가 나왔고, 진짜 held-out으로 고치니 74.5%였습니다.
→ 논문에 정확도를 쓸 때 어느 분할에서 나온 수치인지 반드시 명시해야 합니다.

25 p9 #144 has_bbox 채널의 의미 — 검출 실패 시 cx=0.5, cy=0.6, area=0.06의 고정 fallback 값이 들어가고 has_bbox=0으로 표시됩니다. 즉 헤드는 "지금 타겟을 못 보고 있다"는 신호를 입력으로 받습니다. 그런데 학습 데이터에는 has_bbox=False 프레임이 0.00%(0/16,599)여서, 모델은 이 신호에 대응하는 법을 배운 적이 없습니다(CH64 64-15). 실기에서는 이를 학습이 아니라 서빙 제어 로직으로 우회했습니다(4절).

✅ 대응책 — 무엇으로 채우는가

그대로 유지 가능합니다. fallback 값(cx 0.5 / cy 0.6 / area 0.06), has_bbox=0 표시, 학습 데이터 0.00%(0/16,599), 서빙 우회 — 전부 실측과 일치합니다.
