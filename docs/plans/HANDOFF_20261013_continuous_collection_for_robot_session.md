# 핸드오프: 연속 조이스틱 수집 개선 (학습 서버 → 로봇/수집 세션)

> 작성: 2026-10-13 (학습 서버 minum 세션) | 대상: 로봇/Jetson 수집 세션
> 읽는 순서: §1 요청 → §2 근거(신규 데이터 분석) → §3 2026 논문 조사 → §4 파일럿 합격 기준
> 점검 스크립트: `python3 scripts/check_continuous_collection_quality.py [dir] [--per-episode]` (수집 직후 바로 돌려볼 수 있음)

## 1. 로봇 세션에 요청하는 것 (우선순위 순)

1. **조이스틱 → 저장값 변환 확인 후 공유**: 데드존, 게인(1.1배라는 얘기가 있음), 클리핑 순서, 샘플링 주기(실측 6.6Hz). 데이터에서는 비영 최솟값이 0.16대(데드존 약 0.16 추정), 최댓값이 1.0이다.
2. **원값 저장**: 게인·클립을 적용하기 전의 스틱 값을 `actions_raw`로 함께 저장(기존 `actions`는 유지). 학습 시점에 게인을 적용하는 편이 정보 손실이 없다. 현재 포화율(lx 72%, ly 91%)에는 게인+클립 효과가 섞여 있을 수 있다(미확인).
3. **프레임별 실제 이동량 로깅**: 가능하면 `odom`(휠 오도메트리 또는 IMU) 또는 실제로 적용된 `cmd_vel`, 프레임 타임스탬프. 2026 내비 논문들은 조이스틱 값 자체보다 **궤적/waypoint를 복원해 학습 타깃으로 쓴다**(§3). 스틱이 포화돼도 실제 이동 궤적에서 연속 타깃을 만들 수 있다.
4. **주행 방식 파일럿 (10 에피소드)**: 스틱을 끝까지 밀지 말고 **비례 조향**(목표가 중앙에서 벗어난 만큼만 ly), 목표 가까이에서 감속(lx 줄이기), 느림/보통/빠름 속도 프로파일을 에피소드마다 다르게. 가능하면 **최대 속도 게인을 낮춰** 평소 주행이 스틱 행정의 30~80%에서 일어나게.
5. **스틱 매핑 점검**: 지금은 (lx, ly)가 축별 독립이라 대각선이 (1,1) 코너로 눌린다(크기 최대 1.41). 원형 게이트 또는 (속력, 방향각) 분해를 쓰면 각도가 연속으로 나온다. 우측 곡선을 strafe 대각선만이 아니라 ang_z와 섞는 방안도 검토.
6. **ang_z 한 프레임 튐 확인**: ang_z 비영 42개 중 15개가 앞뒤가 0인 단독 스파이크 → 버튼/축 오입력 가능성.
7. **경로 다양성**: 현재 23ep는 center_right_curve 20 + center_straight 3뿐. 학습에는 방향(5)×곡선(3) 조합과, 바구니가 시야 밖인 **부재 프레임**(has_bbox 판정 기준용)이 필요.
8. 위 파일럿 후 `check_continuous_collection_quality.py` 결과를 커밋 메시지나 노트로 공유.

## 6. 로봇 세션 수정안(raw/scaled + 원형게이트 + az 디바운스) 리뷰 — 학습 서버 측 (2026-10-13)

> 근거: 로봇 세션이 공유한 설명서 + 이 repo의 이전 버전 `robovlm_nav/serve/mona_dashboard.py:955~985`. **수정된 코드 자체는 아직 푸시되지 않아 설명서 기준으로만 검토**했다.

**좋은 점**: 원값/구동값 동시 저장, 원형 게이트(방향 비율 보존 → 45° 코너 고정 해소), az 디바운스(단독 스파이크 대응).

**확인·요청 (중요도 순)**
1. **`actions` 의미 변경**: v1은 `actions`=구동값, v2는 `actions`=원값(크기 최대 1.41). 기존 로더가 `actions`를 그대로 읽으므로 `action_space` 속성을 올리고(예: `egvla2_continuous_v2`), `action_classes`의 계산 원천(raw/scaled)을 알려줄 것. 학습 타깃은 `actions_scaled` 권장.
2. **v1과 v2 혼합 금지**: v1은 축별 클리핑이라 대각선 속도 최대 1.41, v2는 원형 게이트라 1.0 — 물리 속도가 다름.
3. **데드존 불연속**: 축별 `|v|>0.15`면 원값 → 0↔0.16 사이가 비고, (0.9,0.14)에서 0.14가 지워져 방향 비율이 틀어짐. 벡터 크기 기준 방사형 데드존 + `(|v|-0.15)/(1-0.15)` 재조정을 원형 게이트 앞에 적용 권장.
4. **이전 경로 우회 확인**: 이전 코드는 아날로그 축을 `_axis_to_key`(임계 0.50)로 8키 변환 후 `WASD_TO_VEL`(±1.15 고정)을 곱한다(사실상 키보드 에뮬레이션). 새 경로가 이를 우회하는지, `JITTER_HOLD`(중립 후 0.3초 동안 마지막 키 재전송)가 `actions`에 스틱을 놓은 뒤 최대값을 연장해 기록하지 않는지, `az_blend*0.15` 처리를 확인할 것.
5. **속도 슬라이더 기록**: `joystick_speed`→`_speed`, 속도는 `speed/1.15`배. 신규 데이터 최댓값이 1.0인 것도 이 설정 때문일 수 있음. 에피소드 attrs에 속도 설정 저장.
6. **디바운스 80ms**는 10Hz 발행(100ms)·프레임 주기(약150ms)보다 짧아 한 프레임 스파이크가 걸러지지 않을 수 있음. 수정 후 `check_continuous_collection_quality.py`의 "ang_z 단독 스파이크"가 0에 가까워지는지 확인.
7. **여전히 누락**: odom/실제 cmd_vel/프레임 타임스탬프. 6.6Hz 프레임과 10Hz 발행이 어긋나므로 프레임에 저장되는 값이 마지막 발행값인지 구간 평균인지 정의할 것.

## 7. 로봇 세션 회신 — §6 리뷰에 대한 코드 수준 확인 (2026-10-13)

> 코드는 이미 푸시되어 있음: `robovlm_nav/serve/mona_dashboard.py`(`DashboardJoystickReader._loop`, `DataCollectSession`), `robovlm_nav/serve/vla_control_utils.py`(`VLAControlManager.publish_and_move`/`move_and_stop_timed`). **아래 1·2·4만 코드 레벨로 확인/반영 완료 — 3·5·6·7은 아직 미반영, 다음 턴에 진행 예정.**

**완료**
1. **`action_space` 버전업 반영**: `f.attrs["action_space"] = "egvla2_continuous_v2"`로 올림. `action_classes`는 `actions_scaled`(실제 구동값, `d["action"]`)에서 계산 — raw가 아님. 학습 타깃은 말씀대로 `actions_scaled` 권장 기준에 맞춰져 있음.
2. **v1/v2 혼합 없음 확인**: raw/scaled 분리+원형게이트 코드가 실제 배포된 시점(2026-10-13 17:36) 이후 수집이 없었음을 파일 타임스탬프로 확인. 현재 쌓인 egvla2 디렉토리 39건은 전부 `action_space=egvla2_continuous_v1`(`actions_scaled` 데이터셋 자체가 없음)이고, v2 배포(17:46) 이후로는 새 포맷만 쌓임 — 같은 디렉토리 안에서도 섞이지 않았음.
4. **이전 경로 우회 확인**: `_loop()` 재확인 결과, `WASD_TO_VEL` 고정테이블은 `else`(continuous 아닐 때) 분기에만 있어 continuous 분기(`vel = (lx*spd, ly*spd, az*spd)`)와 if/else로 완전 분리. `JITTER_HOLD`는 이산 방향 라벨 `key` 변수만 0.3초 유지시키고, continuous 분기가 쓰는 lx/ly/az 자체는 매틱 실시간값 그대로라 "놓은 뒤 최댓값을 연장 기록"하는 경로는 없음. `az_blend*0.15`도 discrete 분기 전용이라 continuous엔 적용 안 됨.

**미반영 — 진행 예정**
3. 방사형 데드존 — 현재 축별 `rd(idx)` 컷이 그대로 raw_vel 계산 전에 들어가 있어, 말씀하신 `(0.9,0.14)→0.14 소실` 문제가 raw에도 그대로 남아있음. 벡터 크기 기준 데드존 + 재조정 반영 예정.
5. 속도 슬라이더(`self._speed`) 값을 attrs에 저장하는 것 — 아직 미반영.
6. 디바운스 창(현재 2폴≈80ms) — 지적하신 대로 실제 프레임 주기(~150ms)보다 짧아 그 근처 지속시간의 글리치를 못 거를 수 있음. 창 확대 예정.
7. odom/cmd_vel/프레임 타임스탬프 로깅 — 아직 착수 전.

  - **odom/실제 cmd_vel 피드백은 여전히 불가** — repo 전체에 `Odometry` 구독 코드 자체가 없음(`grep` 결과 0건). `/cmd_vel`은 퍼블리시만 하고 실제 구동은 `pop.driving.Driving` 하드웨어 직접 호출이라 ROS 피드백 루프가 없음. 센서/펌웨어 쪽 작업이 필요한 하드웨어 갭이라 코드로는 못 채움 — 추가 센서 없이는 이 항목은 보류.

**원형게이트(circular gate) 설계의 선행사례 조사**: "벡터 크기 계산 후 방향 유지·크기만 정규화"가 임의 설계가 아닌지 확인 요청이 있어 조사함.
- **게임/컨트롤러 입력 처리**: radial deadzone이 표준 기법. Unity의 공식 Stick Deadzone 프로세서가 거의 동일한 2단계(벡터 크기 임계값 → 남은 구간 0~1 재조정)를 수행. 축별(per-axis) 데드존이 대각선 저크기 입력에서 방향을 축 쪽으로 왜곡시킨다는 게 업계 공통 지적.
- **RL 액션 공간 설계**: 지오데식 생성 Actor-Critic RL(arXiv:2407.01991)이 2D 각도 성분을 [-1,1] 박스로 clamp한 뒤 단위원에 정규화 — 원형게이트와 수학적으로 동일. 2025년 unit-norm 액션 파라미터화 논문(방향벡터+세기 스칼라 분리)도 ablation에서 이 정규화가 학습 안정성에 필수였다고 보고.
- **텔레옵 모방학습**: VR 텔레옵 논문(Zhang et al., arXiv:1710.04615)이 "크기보다 방향이 중요하다"며 별도 각도 손실 항을 추가 — 우리의 "방향 우선, 크기는 보조" 설계와 같은 결론.
- **한계**: "조이스틱 원형게이트"를 직접 다룬 로보틱스/텔레옵 논문은 못 찾음. 다만 게임 입력 처리(①)와 RL 액션 전처리(②) 각각에서 독립적으로 검증된 기법을 결합한 것이라 설계 리스크는 낮다고 판단.

## 9. 학습 서버 측 코드 리뷰 — 푸시된 `62e722bc` 실제 코드 기준 (2026-10-13)

**확인된 것(보고와 일치)**: `action_space=egvla2_continuous_v2`, `actions`=raw/`actions_scaled`=구동값, `action_classes`는 구동값에서 역산, `frame_timestamps`·`action_value_semantics`·`joystick_speed_setting` 저장, 방사형 데드존+재조정, 원형게이트(mag>1 정규화), az 200ms 경과시간 디바운스, continuous 분기는 `WASD_TO_VEL`·`az_blend` 미사용.

**문제 (중요도 순)**
1. **`if key:` 게이트가 중간값을 지운다 (가장 큼)**: 발행은 `key = _axis_to_key(lx,ly,az)`(THRESHOLD 0.50)가 None이 아닐 때만 일어난다. 세 축 모두 |v|<0.5이면 key=None → (JITTER_HOLD 0.3s 이후) 발행·기록 없음 = 사실상 정지. 실제로 v1 40건 비영 2,048프레임 중 `max|v|<0.5`는 **3프레임**뿐이다 — 연속 입력이 있어도 약한 스틱은 기록되지 않는다(이것이 "중간값이 거의 없다"의 한 원인으로 보임). v2는 방사형 재조정으로 실효 데드존이 raw 크기 약 0.575까지 커져 더 심해진다. **수정**: continuous 모드에서는 key 게이트 대신 `mag>0`(또는 `|az|>0`)이면 발행하고, key는 UI 라벨용으로만 쓸 것. 파일럿 합격 기준(중간값 ≥50%)은 이 수정 없이는 달성 불가.
2. **실제 구동은 크기를 쓰지 않는다**: `publish_and_move`는 `driver.move(angle, throttle)` — 각도만 연속이고 속력은 고정 throttle이다. `lx,ly` 크기(0.3 vs 1.0)가 물리 속도에 반영되지 않는다. 그러면 `actions_scaled`의 크기는 로봇이 실제로 낸 속도가 아니라 라벨일 뿐이어서, 명령 적분으로 궤적을 복원해도 크기 성분이 틀린다. 선택: (a) 크기를 throttle에 반영(`throttle×mag`)하거나, (b) 속력 연속값을 라벨에서 제외하고 "방향각 연속+고정 속력"으로 문서화(학습 타깃도 각도 중심). 어느 쪽인지 결정 필요.
3. **회전과 이동이 동시에 기록되지만 구동은 회전만**: `|az|>0.1`이면 `driver.spin`만 호출하고 이동은 무시한다. 기록값은 (lx,ly,az) 동시값이라 라벨과 실제가 어긋난다. 동시 입력 시 az를 0으로 기록하거나, 구동도 혼합하도록 맞출 것.
4. **raw가 1.0을 넘을 수 있음**: 사각 게이트 패드에서 대각선 풀 입력이면 `mag_axis`≈1.41 → 재조정 후 raw 크기 ≈1.46. `actions`(raw) 범위를 문서화하고, 학습은 `actions_scaled`를 쓸 것.
5. **az에는 방사형 처리가 없다**: 축별 `rd()` 컷 + 200ms 홀드. 200ms 홀드는 진짜 짧은 회전 입력도 지운다. 단독 스파이크가 0인지는 데이터로 확인해야 한다.
6. **프레임 저장이 발행 시점**: `on_command`가 호출될 때마다 프레임을 추가한다(≈10Hz 상한, 연속 STOP은 1개로 압축). `frame_timestamps`로 실제 간격을 보고 학습 쪽에서 리샘플 여부를 정한다.

## 10. 제안: 단일 기준값(raw)에서 A/B/C 변환 라벨을 파생하는 저장 구조 (학습 서버 → 로봇 세션, 2026-10-13)

> §9 #1·#2 대응. **로봇 세션이 수정할 사안이며, 사용자 승인 후 적용.** 구동 방식(속력 처리)은 아래 §10.3에서 선택.

### 10.1 입력 현황 (코드 + `scripts/joystick_config.json`, DragonRise 강제 레이아웃)
- 주행 아날로그 축 3개: 왼쪽 스틱 Y(축1)→`lx`, 왼쪽 스틱 X(축0)→`ly`, 오른쪽 스틱 X(축2)→`az`. 값 -1~1, 데드존 0.15. 오른쪽 스틱 Y·트리거는 미사용.
- 기능 버튼 8개(STOP, 실험표기 토글, 폐기, 수집↔검증, 녹화시작, 정지·저장, 녹화토글, SYNC↔ASYNC) + 복귀 1개 + D-pad(시나리오/위치 순환). **학습 데이터에 들어가는 입력은 축 3개뿐**이고 버튼·D-pad는 메타데이터.

### 10.2 저장 구조
| 필드 | 내용 | 용도 |
|---|---|---|
| `actions_raw` | 방사형 데드존만 통과한 (lx,ly,az) | 모든 변환의 기준 |
| `actions_exec` | 로봇에 실제로 내려간 값(각도, throttle 단계, 회전 여부) | 실제로 일어난 일 |
| `actions_A` | 원형게이트 정규화(크기 보존) | 속력+방향 의도 |
| `actions_B` | (각도=atan2(ly,lx), GO/STOP) | 방향 중심 |
| `actions_C` | (각도, 속력 단계 0~3: 크기 임계 2개) | 방향+단계 속력 |
| `frame_timestamps` | 프레임별 시각 | 적분·리샘플 |

attrs: `derive_version`(변환식·임계값 버전), `drive_mode`, `joystick_speed_setting`, `throttle_levels`, `action_space`(v3 등으로 올림).
- 변환 대상은 (lx,ly) 2축. `az`는 그대로 저장하되 구동은 `|az|>0.1`이면 회전만 하므로 `actions_exec`에 그 규칙을 반영.
- A/B/C는 학습 로더에서 `actions_raw`로 재생성해도 되고(규칙 변경 시 재변환 가능, 권장), 파일에 미리 저장해도 된다(이때 `derive_version` 필수).

### 10.3 구동 방식과 라벨의 정합성 (핵심)
로봇은 한 가지로만 움직인다. 현재 구동은 각도+고정 throttle이라 A·C의 속력은 **스틱 의도**일 뿐 영상의 움직임과 무관하다(라벨-영상 불일치 노이즈). 따라서 구동을 정해야 한다.
- **권장**: 구동을 C(속력 3단계, 실제 throttle 변경)로 하고 raw를 함께 저장 → C는 실제와 일치, B는 방향 라벨(속력 섞임), A는 근사.
- 단계별 throttle→실제 속도는 고정 거리 스톱워치로 보정(odom 없음).
- 보류: A(크기→throttle 연속)는 odom 전까지 검증 수단이 없어 제외.

### 10.4 선결 수정 (§9 #1)
`if key:`(THRESHOLD 0.5) 게이트 때문에 약한 스틱이 발행·기록되지 않으면 어떤 변환도 빈 입력이다. continuous에서는 `mag>0`이면 발행하고 key는 UI 라벨용으로만 쓸 것.

### 10.5 수정 대상·검증
- `mona_dashboard.py` `_loop`(게이트·변환), `_save_episode_data`(필드), `vla_control_utils.py`(구동 모드).
- v2 파일럿 10ep 도착 시 학습 서버가 `check_continuous_collection_quality.py`를 `actions_raw`/`actions_exec` 기준으로 확장해 중간값≥50%·코너≤20%·스파이크≈0과 속력 단계 분포를 판정한다.
- v1·v2·v3 혼합 금지.

### 12.1 먼저 결정된 것 (사용자, 2026-10-14)
- 속력은 3-class가 아니라 **연속값으로 취급**한다. 추론은 모델 출력 크기를 [0.4, 1.0]로 잘라 `throttle_scale`로 쓰고 중간 속력은 선형 보간으로 지정한다(중간값 선형성 추가 측정 불필요). → 로봇 세션이 추가로 보정할 것은 없다. (`plan_20261014_inference_continuous_speed.md`)
- 수집 구동은 **지금의 3단계(방식 C) 그대로** 유지. 구동 방식 변경은 이번 범위 밖.

### 12.2 데이터에서 읽은 "스틱 크기 → 속력 단계" 경계 (v3 28건 역산)
| exec 단계 | raw (lx,ly) 크기 범위 | 비고 |
|---|---|---|
| 느림 0.4 | ≤ 0.35 (p95 0.34) | |
| 보통 0.7 | 0.35 ~ 0.70 | |
| 빠름 1.0 | ≥ 0.70 | **0.7~0.9도 빠름**이라 "0.15~0.9 중간값"과 "속력 단계"가 일치하지 않는다 |

⚠ 푸시된 코드(`62e722bc`)에는 §11의 구동 C·게이지 변경이 없어 코드 상수를 확인하지 못했다. 위 경계(≈0.35, ≈0.70)는 데이터 역산값이므로 **코드의 실제 임계값과 일치하는지 확인**하고, 다르면 알려 달라(변경분 푸시도 요청).

### 12.3 수집 속력 가이드 — 어떤 경향으로 운전하나
파일럿 v2의 에피소드 진행도별 평균 크기: 0~10% 0.42 → 10~30% 0.67 → 30~70% 0.72 → 70~90% 0.62 → 90~100% 0.44 (느림 → 보통~빠름 → 감속 → 느림).
| 에피소드 구간 | 목표 스틱 크기 | 단계 | 비고 |
|---|---|---|---|
| 시작 0~10% | 0.30~0.50 | 느림~보통 | 부드럽게 램프업 |
| 10~70% | 0.50~0.90 | 보통~빠름 | 방향을 크게 바꾸는 곡선 구간은 보통(≈0.5~0.65)으로 |
| 70~90% 목표 접근 | 0.55 → 0.35 | 보통 → 느림 | 바구니가 커질수록(가까울수록) 서서히 감속 |
| 마지막 10% | < 0.35 | 느림 | 이후 STOP |
- **한 에피소드에서 3단계를 모두 한 번 이상** 쓰기. 세트 전체 분포 목표: 느림 15~25%, 보통 35~45%, 빠름 35~45% (파일럿 v2 17/39/43%).
- 경계(0.35, 0.70) 바로 위에서 **떨지 않기**: 경계 근처에서 흔들리면 단계 라벨이 깜빡인다. 경계에서 확실히 벗어난 값(예: 0.25/0.5/0.85)을 목표로.
- 직선·좌·우 곡선 모두 같은 프로파일(시작 느림 → 중간 빠름 → 접근 감속). 에피소드마다 약간씩 다르게(운전 습관 편차 0.65~0.92는 이미 큼).
- **엄격 고정이 아니다.** 가이드대로 하되 부자연스럽게 맞추지 말 것. 분석 결과 현재 속력은 바구니 거리와 상관이 거의 없다(ρ=−0.06) — 이 가이드는 그 상관을 만들기 위한 것이다.

### 12.4 📷 수집 탭 "스틱 세기" 게이지 설정 제안
현재 요소: 🎚️ 스틱 세기 바 / 0.15~0.9 목표구간 / 1.0+ / 🎯 중간값 통과 목표(50%) / 📈 최근 세기 흐름.
| 요소 | 제안 설정 | 이유 |
|---|---|---|
| 스틱 세기 바 눈금 | **0.35, 0.70에 세로선**, 구간 색 — 0.15~0.35 파랑(느림) / 0.35~0.70 초록(보통) / 0.70~1.0 노랑(빠름) / 1.0+ 빨강(포화) | 지금의 "0.15~0.9 목표" 한 구간은 속력 단계를 구분하지 못한다 |
| 중간값 비율 | 정의 유지: 크기가 0.15~0.9인 비영 프레임 비율. 통과 목표 **50% 유지**(파일럿 v2 75%) | 공식 품질 판정(CH76-6)과 같은 정의 |
| 🎯 목표 막대 | 추가로 **속력 단계 분포 막대**(현재 세션 누적 느림/보통/빠름 %) + 목표 범위 표시(15~25 / 35~45 / 35~45) | 빠름이 55%를 넘으면 노랑 경고 |
| 📈 최근 세기 흐름 | 위 구간선(0.35/0.70)을 같이 그리고, 가능하면 **에피소드 진행도별 목표 프로파일**(12.3 표)을 연한 밴드로 겹쳐 표시 | 운전 경향을 눈으로 맞추기 쉽게 |
| 경계 진동 경고 | 최근 2초 중 0.33~0.37 또는 0.68~0.72에 머문 비율이 30% 넘으면 "경계 근처" 표시 | 단계 라벨 깜빡임 방지 |
| 포화/코너 | 크기 ≥1.0(빨강) 비율 표시, 코너(lx,ly 동시 포화) 20% 넘으면 경고 | 합격 기준(코너 ≤20%) |
| 중간값 계산 단위 | 스틱 값이 아니라 **raw 크기 √(lx²+ly²)** 기준으로 통일 | 학습 쪽 공식 지표와 동일 |
