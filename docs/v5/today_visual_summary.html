2Detector 교체 검토 — GroundingDINO vs YOLO-World vs base PG2

PG2를 다른 detector로 바꾸면 더 나을지 같은 8프레임에 세 모델을 나란히 비교했다.

기준

탈락
GroundingDINO-tiny — latency 18배 빠르지만 OOD 오탐 100%(의자 11장 전부 오탐)
탈락
GroundingDINO-base — 더 무거운데도 OOD 오탐 91%, 별로 개선 안 됨
애매함

⚠️ 결론: 둘 다 PG2를 깨끗하게 못 이김 — GDINO는 OOD에서, YOLO-World는 진짜 어려운 케이스 recall에서 막힘. production 교체 보류.
3S6 dead-zone — "이미 멈춘 뒤에 일어난 일이었다"

frame 24에서 학습된 STOP이 한 번 발동하면 105프레임 끝까지 안 풀린다. 그러니까 56/70/85에서 본 grounding 흔들림은 로봇이 이미 정지한 뒤 벌어진 일 — 실제 동작에는 영향이 없었다는 게 오늘 STOP 로직 재생(replay)으로 새로 밝혀진 사실.

f24 — STOP 발동
학습된 헤드가 여기서 STOP 예측, 이후 끝까지 0/82 복귀

f85(STOP 이후)

✅ 결론: "dead-zone 풀프레임 환각"은 실재했지만 로봇 동작에는 영향 없었음 — STOP이 이미 21프레임 전에 걸렸기 때문.
4S7 near-miss — "진짜 근접인데 1프레임짜리라 놓쳤다"

frame 53에서 area=0.297로 GOAL_AREA(0.25)를 실제로 넘었다 — bbox 자체는 정상. 문제는 앞뒤 프레임이 못 따라가서 3프레임-연속 조건(GOAL_CONSEC_FRAMES=3)에 걸려 STOP이 끝까지 발동하지 않았다는 것.

f52
area=0.072 — 아직 멀음
f53 — 진짜 스파이크
area=0.297(임계 초과!), cx=0.673 — 그런데 단 1프레임
f54
area=0.070 — 바로 다시 멀어짐, 3연속 조건 실패 → STOP 무산
⚠️ 결론: detector를 GroundingDINO나 YOLO-World로 바꿔도 똑같이 놓쳤을 것 — 이건 grounding 문제가 아니라 STOP 로직(연속프레임 조건)의 부작용이었다.
5S8 — "거짓양성도 똑같이 위험할 수 있다"

GOAL_CONSEC_FRAMES를 1로 낮추면 S7은 잡지만, 실제 운영 로그(S8, mix-448)의 frame 20처럼 스폿체크로 이미 거짓양성 확인된 프레임에서도 false STOP이 발동한다 — n=2도 n=3과 동일하게 효과 없음.

f20 — 확인된 거짓양성
area=0.532(임계 압도적으로 초과)인데 스폿체크로 실제 바스켓이 아님이 확인된 프레임. GOAL_CONSEC_FRAMES=1이면 여기서 false STOP 발동.
💡 결론: "진짜 단발 근접"(S7 f53)과 "거짓양성 단발 스파이크"(S8 f20)를 area+cx+연속프레임만으로는 구분 못 함 — consec_n 숫자 조정은 더 이상 유효한 레버가 아니다. 운영값(n=3) 유지 권장.
6"방향 신호가 약하다"의 실체 — 4개 실제 세션에서 실제 출력으로 확인

38-4에서 hidden state 코사인거리로 "방향 신호가 객체 신호보다 10배 약하다"고 했는데, 숫자만으로는 안 와닿을 수 있다. 그래서 실제 PG2가 무엇을 생성하는지(raw 텍스트 출력)를 4개의 서로 다른 실제 바스켓 세션 사진(S6 baseline·S6 dead-zone·S7 정상검출·S8 production)에서 직접 확인했다.

S6 baseline (frame 1) — 초록 박스 = detect 출력 그대로
detect → <loc0483><loc0441><loc0714><loc0579>
detect+left → 동일 좌표
detect+right → 동일 좌표
nav_left → 'yes<eos>'
nav_right → 'yes<eos>'
S6 dead-zone (frame 70) — 박스가 세로로 거의 풀프레임
detect → <loc0000><loc0451><loc0951><loc0726>
detect+left/right → <loc0460>...(±1픽셀급 차이, 노이즈 수준)
nav_left/right → 둘 다 'yes<eos>'
S7 정상검출 (frame 84) — 타이트하게 정상 검출
detect → <loc0478><loc0290><loc0833><loc0499>
detect+left/right → 동일(±1 노이즈)
nav_left/right → 둘 다 'yes<eos>'
S8 production·mix-448 (frame 8) — 박스가 바구니보다 넓게 잡힘
detect → <loc0462><loc0591><loc0857><loc0822>
detect+left/right → 동일(±1 노이즈)
nav_left/right → 둘 다 'yes<eos>'
대조군 — 진짜 다른 객체(사과), 박스가 사과를 정확히 잡음
detect green apple → <loc0559><loc0464><loc0671><loc0561> (바스켓과 완전히 다른 좌표)
→ 객체가 진짜 바뀌면 출력도 확실히 바뀐다
⚠️ 정정된 결론: "방향 신호가 약하다"는 사실 출력 레벨에서는 신호가 거의 없다(0에 가깝다)가 더 정확하다. 4개 세션 전부 동일하게 — ① "detect ... on the left/right"로 줘도 bbox가 노이즈 수준 차이(±1픽셀급)로만 다르고, ② "Navigate to the left/right"는 PG2가 이걸 detection task로 인식조차 못 하고 전부 'yes'라고만 답한다. 반면 객체 자체가 바뀌면(사과 대조군) bbox가 완전히 다른 위치로 바뀐다 — "무엇을 보는가"는 잘 바뀌지만 "어느 쪽을 보라는 지시"는 사실상 안 들어간다. 38-4의 cos_dist 0.03~0.05는 "약한 신호"가 아니라 "행동으로 안 이어지는 미세한 내부 흔들림"으로 재해석해야 한다.
