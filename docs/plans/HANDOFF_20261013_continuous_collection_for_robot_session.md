# 핸드오프: 연속 조이스틱 수집 개선 (학습 서버 → 로봇/수집 세션)

> 작성: 2026-10-13 (학습 서버 minum 세션) | 대상: 로봇/Jetson 수집 세션
> 읽는 순서: §1 요청 → §2 근거(신규 데이터 분석) → §3 2026 논문 조사 → §4 파일럿 합격 기준
> 점검 스크립트: `python3 scripts/check_continuous_collection_quality.py [dir] [--per-episode]` (수집 직후 바로 돌려볼 수 있음)

## 1. 로봇 세션에 요청하는 것 (우선순위 순)

1. **조이스틱 → 저장값 변환 확인 후 공유**: 데드존, 게인(1.1배라는 얘기가 있음), 클리핑 순서, 샘플링 주기(실측 6.6Hz). 데이터에서는 비영 최솟값이 0.16대(데드존 약 0.16 추정), 최댓값이 1.0이다.
2. **원값 저장**: 게인·클립을 적용하기 전의 스틱 값을 `actions_raw`로 함께 저장(기존 `actions`는 유지). 학습 시점에 게인을 적용하는 편이 정보 손실이 없다. 현재 포화율(lx 72%, ly 91%)에는 게인+클립 효과가 섞여 있을 수 있다(미확인).
3. **프레임별 실제 이동량 로깅**: 가능하면 `odom`(휠 오도메트리 또는 IMU) 또는 실제로 적용된 `cmd_vel`, 프레임 타임스탬프. 2026 내비 논문들은 조이스틱 값 자체보다 **궤적/waypoint를 복원해 학습 타깃으로 쓴다**(§3). 스틱이 포화돼도 실제 이동 궤적에서 연속 타깃을 만들 수 있다.
4. **주행 방식 파일럿 (10 에피소드)**: 스틱을 끝까지 밀지 말고 **비례 조향**(목표가 중앙에서 벗어난 만큼만 ly), 목표 가까이에서 감속(lx 줄이기), 느림/보통/빠름 속도 프로파일을 에피소드마다 다르게. 가능하면 **최대 속도 게인을 낮춰** 평소 주행이 스틱 행정의 30~80%에서 일어나게.
5. **스틱 매핑 점검**: 지금은 (lx, ly)가 축별 독립이라 대각선이 (1,1) 코너로 눌린다(크기 최대 1.41). 원형 게이트 또는 (속력, 방향각) 분해를 쓰면 각도가 연속으로 나온다. 우측 곡선을 strafe 대각선만이 아니라 ang_z와 섞는 방안도 검토.
6. **ang_z 한 프레임 튐 확인**: ang_z 비영 42개 중 15개가 앞뒤가 0인 단독 스파이크 → 버튼/축 오입력 가능성.
7. **경로 다양성**: 현재 23ep는 center_right_curve 20 + center_straight 3뿐. 학습에는 방향(5)×곡선(3) 조합과, 바구니가 시야 밖인 **부재 프레임**(has_bbox 판정 기준용)이 필요.
8. 위 파일럿 후 `check_continuous_collection_quality.py` 결과를 커밋 메시지나 노트로 공유.

## 2. 근거: 신규 데이터(23ep, 1,417프레임) 분석 요약

| 항목 | 값 |
|---|---|
| 샘플링 | 6.6Hz(프레임 간격 151ms), joystick 1,302 + stop_inject(합성 0 액션) 115 |
| 범위 | 3축 모두 [-1,1], 0.01 해상도, (lx,ly) 크기 최대 1.41 (원형 게이트 아님) |
| 포화(|v|≥0.99) | lin_x 72%, lin_y 91%, ang_z 81% (비영 프레임 기준) |
| 비포화(0<\|v\|<0.99) | lin_x 약 28%, lin_y 약 9% |
| 중간값(0.15<\|v\|<0.9) | lin_x 21%, lin_y 8% |
| 코너(lx,ly 둘 다 ±1) | lx·ly 둘 다 비영인 886프레임 중 517(58.4%), 방향각 정확히 45°, 연속 유지 중앙 6프레임(최대 30) |
| ang_z | 비영 42개(3%), 그중 15개는 단독 스파이크 |
| 클래스 일치 | 저장된 `action_classes`가 V6 임계값 규칙과 100% 일치 |
| 경로 일관성 | center_right_curve: ly<0(우측) 75%, 앞 1/3 ly 포화 98% → 뒤 1/3 26% (목표 근처에서 풀어줌) |

해석: 값은 경로와 잘 맞지만 대부분 스틱이 끝까지 눌려 사실상 on/off(키보드와 유사)다. 연속 정보는 에피소드 앞 램프와 목표 근처에서 풀어주는 구간에만 있다. 연속 액션 헤드(FM 등)를 학습해도 대부분 프레임은 극단값에 몰린 다봉 분포가 된다.
(소프트 라벨 대리 실험으로 부드러운 타깃의 이득을 시험했으나 test PM +0.4%p로 오차 범위. 연속 데이터의 가치는 수집 방식을 바꿔야 커진다.)

## 3. 2026 논문 조사 (arXiv 초록 기준 — 본문 미확인, 수집 세부는 원문 확인 필요)

| 논문 | 수집/표현 방식 (초록에서 확인된 범위) | 우리에게 주는 시사점 |
|---|---|---|
| **UNI** — Universal Navigation Interface (2609.20114) | 로봇 없이 롤레이터+스마트폰으로 인간 시연 수집, **미터 궤적(metric trajectory)을 복원**해 지도, 37.2km | 조이스틱 값이 아니라 궤적을 타깃으로. 우리도 odom/궤적 로깅 시 스틱 포화와 무관한 연속 타깃 가능 |
| **TONAV** (2608.22296) | position-velocity-coupled 텔레옵으로 **매끄럽고 시간적으로 일관된 시연**을 수집, velocity chunk 학습 | 속도 chunk를 쓰는 우리 구조와 가깝고, "수집 단계에서 매끄러움을 확보"한다는 점이 핵심 |
| **Hydra** (2608.28995) | 이산 잠재 계획 + **conditional Flow Matching으로 연속 실행 궤적** 생성, 두 실로봇 | 이산 의도 → FM 연속 실행 분업. 우리 "서브골 + FM"과 유사한 방향 |
| **GemNav** (2607.06882) | waypoint를 **이산 토큰**으로, 연속 회귀 헤드 없음, soft-decoded 보조 손실로 metric 구조 복원, 8.7시간 | 이산 토큰도 소규모 데이터에서 실용적. 단, 이미지 히스토리는 로봇 이득이 없었다고 보고 |
| **Co-training w/ egocentric video** (2606.01951) | 사람 보행 영상에서 카메라 모션을 추정해 지상 로봇 액션 표현으로 변환, 로봇 데이터와 공동 학습 | 로봇 수집량 보완 수단. 연속 액션 표현이 카메라 모션에서 나온다는 점 |
| **PanoVLA / whole-body teleop** (2608.02257) | VR 단일 인터페이스로 전신 시연, 5.5시간 | 연속 텔레옵 인터페이스 사례(조작 중심) |
| **Phone2Act** (2605.01948) | 저가 스마트폰 기반 텔레옵 시스템 | 저비용 연속 입력 장치 대안(조작 중심) |
| **Self-Imitated Diffusion Policy** (2601.22965) | 표준 IL이 시연의 비최적·중복을 그대로 학습하는 문제를 지적 | 시연 품질(중복·잉여 동작) 관리 필요 |

공통 경향(초록 기준): 내비 쪽은 **조이스틱 원값보다 복원된 궤적·waypoint를 학습 타깃**으로 쓰는 사례가 많고, 연속 생성 헤드(FM/diffusion)를 쓰는 경우 시연의 **매끄러움**을 수집 단계에서 확보하려 한다.
한계: 위 내용은 초록 수준이며 조이스틱 매핑·게인 같은 세부는 본문에서 확인하지 못했다. 필요하면 해당 논문 본문을 추가로 읽을 것.

## 4. 파일럿 합격 기준 (제안, 합의 필요)

- 중간값(0.15~0.9) 비율: lx 또는 ly 50% 이상
- 코너(lx,ly 동시 포화) 비율 20% 이하
- ang_z 단독 스파이크 0에 가깝게
- 에피소드 전 구간에 중간값 분포 (현재는 앞쪽 램프와 중반에 편중)
- 프레임별 odom/cmd_vel 로깅 확인
현재 23ep 기준값(미달): 중간값 lx 21%/ly 8%, 코너 58%, 스파이크 15/42.

## 6. 로봇 세션 수정안(raw/scaled + 원형게이트 + az 디바운스) 리뷰 — 학습 서버 측 (2026-10-13)

> 근거: 로봇 세션이 공유한 설명서 + 이 repo의 이전 버전 `robovlm_nav/serve/mona_dashboard.py:955~985`. **수정된 코드 자체는 아직 푸시되지 않아 설명서 기준으로만 검토**했다.

**좋은 점**: 원값/구동값 동시 저장, 원형 게이트(방향 비율 보존 → 45° 코너 고정 해소), az 디바운스(단독 스파이크 대응).

**확인·요청 (중요도 순)**
1. **`actions` 의미 변경**: v1은 `actions`=구동값, v2는 `actions`=원값(크기 최대 1.41). 기존 로더가 `actions`를 그대로 읽으므로 `action_space` 속성을 올리고(예: `egvla2_continuous_v2`), `action_classes`의 계산 원천(raw/scaled)을 알려줄 것. 학습 타깃은 `actions_scaled` 권장.
2. **v1과 v2 혼합 금지**: v1은 축별 클리핑이라 대각선 속도 최대 1.41, v2는 원형 게이트라 1.0 — 물리 속도가 다름.
3. **데드존 불연속**: 축별 `|v|>0.15`면 원값 → 0↔0.16 사이가 비고, (0.9,0.14)에서 0.14가 지워져 방향 비율이 틀어짐. 벡터 크기 기준 방사형 데드존 + `(|v|-0.15)/(1-0.15)` 재조정을 원형 게이트 앞에 적용 권장.
4. **이전 경로 우회 확인**: 이전 코드는 아날로그 축을 `_axis_to_key`(임계 0.50)로 8키 변환 후 `WASD_TO_VEL`(±1.15 고정)을 곱한다(사실상 키보드 에뮬레이션). 새 경로가 이를 우회하는지, `JITTER_HOLD`(중립 후 0.3초 동안 마지막 키 재전송)가 `actions`에 스틱을 놓은 뒤 최대값을 연장해 기록하지 않는지, `az_blend*0.15` 처리를 확인할 것.
5. **속도 슬라이더 기록**: `joystick_speed`→`_speed`, 속도는 `speed/1.15`배. 신규 데이터 최댓값이 1.0인 것도 이 설정 때문일 수 있음. 에피소드 attrs에 속도 설정 저장.
6. **디바운스 80ms**는 10Hz 발행(100ms)·프레임 주기(약150ms)보다 짧아 한 프레임 스파이크가 걸러지지 않을 수 있음. 수정 후 `check_continuous_collection_quality.py`의 "ang_z 단독 스파이크"가 0에 가까워지는지 확인.
7. **여전히 누락**: odom/실제 cmd_vel/프레임 타임스탬프. 6.6Hz 프레임과 10Hz 발행이 어긋나므로 프레임에 저장되는 값이 마지막 발행값인지 구간 평균인지 정의할 것.
